## 1. 문서 운영 방법

### 1.1. 이 문서에서 관리하는 정보

- **4장:** 시스템별 요구사항의 유일한 관리 목록. 각 행에 구현할 동작과 확인 기준을 기록한다.
- **5장:** 공통 수치와 콘텐츠 고유 수치의 기준표. 다른 곳에서는 해당 ID를 참조한다.
- **6장:** 원문만으로 결과를 결정할 수 없는 질문과 개발 착수 조건. 선택지는 제안이며 채택된 규칙이 아니다.
- **7장:** 정상 동작과 경계 상황의 검증 목록. 실제 실행 결과는 별도의 실행 기록 표에 남긴다.
- **9장:** 개발 순서와 현재 작업. 요구사항 자체를 복제하지 않고 ID로 연결한다.
- **10장:** 중요한 결정과 변경 이유. 과거 규칙을 현재 규칙과 구분한다.

### 1.2. 상태와 갱신 규칙

| 구분 | 사용하는 상태 | 의미 |
|---|---|---|
| 요구사항 정의 | 명시 / 보완 / 후보 | 원문 또는 결정 기록으로 동작이 정해짐 / 일부 결정 필요 / 검토 후보이며 도입 미확정 |
| 개발 | 미확인 / 미착수 / 진행 / 검증 / 완료 / 보류 | 현재 증거를 확인하지 않음부터 실제 검증 완료까지 |
| 결정 사항 | 열림 / 부분결정 / 결정 / 보류 | 질문의 해결 여부. 부분결정은 확정 범위와 남은 질문을, 보류는 재검토 조건을 기록 |
| 검증 결과 | 미실행 / 통과 / 실패 / 차단 | 실제 실행 결과. 규칙 미정으로 실행할 수 없으면 차단 |

1. 기능을 바꾸면 4장의 해당 요구사항을 수정하고, 새 요구사항은 새 ID를 부여한다. 삭제한 ID는 재사용하지 않는다.
2. 수치를 바꾸면 5장의 해당 행을 수정하고 10장에 이유와 재검증 대상을 남긴다.
3. 6장의 질문을 결정하면 결정 기록을 추가하고 영향을 받는 규칙·수치·검증 기준을 함께 갱신한다.
4. 작업을 시작하거나 끝낼 때 4장의 개발 상태와 9장의 작업 기록을 갱신한다. `완료`에는 확인한 빌드나 커밋, 테스트 결과가 필요하다.
5. 원문이 바뀌면 8장의 대응표로 영향 범위를 찾고, 검토 기준일과 원문 해시를 갱신한다. 행 번호는 이 문서 작성 시점의 위치이며 요구사항 ID가 영구 추적 기준이다.

### 1.3. 다른 문서와의 관계

- [Requirements.md](Requirements.md): 사용자가 작성한 원문. 이번 정리에서 변경하지 않았다.
- [Development.md](Development.md): 기존 프로토타입의 임시 규칙·구현·검증 기록. 이 문서의 새로운 규칙이 이미 구현됐다는 근거로 사용하지 않는다.
- `ProjectPlan.md`: 게임 소개와 목표 등 상위 기획 초안. 현재 저장소에는 포함되지 않았다. 원문 요구사항에 없는 내용을 이 문서의 확정 규칙으로 추가하지 않았다.
- [Plan.md](Plan.md): 이전 기획. Requirements.md와 다른 경우 새 요구사항을 개발 검토 대상으로 삼는다.

이번 원문을 반영한 개발용 규칙·수치·진행 상태는 이 문서에서 관리한다. 이후 원문에 변경 요청을 적으면 해당 요구사항 ID와 결정 기록에 반영하고 기준 원문을 갱신한다. 서로 다른 내용을 두 문서에서 동시에 정식 기준으로 유지하지 않는다.

## 4. 시스템별 요구사항과 규칙

요구사항은 독립적으로 확인할 수 있는 동작으로 나눴다. `명시`는 원문 근거가 있다는 뜻이며 검토·승인·구현 완료를 의미하지 않는다. 이후 대화에서 채택한 내용은 10장 결정 ID로 연결하며, 그 범위에 한해 기존 해석보다 우선한다. 보완 항목의 나머지 기대 결과는 6장 결정 이후 확정한다.

### 4.1. 편성과 경기 초기화

**근거:** Requirements.md 1~13행, [기본 게임 흐름](Requirements.md#기본-게임-흐름). **연결:** SYS-MAP, SYS-VIS, SYS-EQUIP.

| ID | 요구사항 | 확인 기준 | 정의 | 개발 |
|---|---|---|---|---|
| R-PRE-01 | 플레이어는 경기 전에 사용할 자기 필드를 구성하고 선택할 수 있다. | 선택한 필드가 자기 진영에 적용된다. | 명시 | 진행 |
| R-PRE-02 | 플레이어는 캐릭터와 장비 아이템으로 덱을 구성한다. | 편성 수가 공통 수치표와 일치하고 유효한 덱만 시작 가능하다. | 보완 Q-11 | 진행 |
| R-PRE-03 | 정해진 두 플레이어가 하나의 경기에 참가한다. | 양측 필드·덱·소유자가 구분된다. | 명시 | 완료 |
| R-PRE-04 | 경기 시작에 자기 필드의 빈 타일을 선택해 기지를 배치한다. | 빈 칸 조건을 만족하며 중립·상대 필드에는 배치되지 않는다. | 보완 Q-20 | 검증 |
| R-PRE-05 | 기지 배치 후 기지가 확보한 시야 안의 자기 필드에 초기 캐릭터들의 위치를 선택한다. | 초기 인원과 배치 순서·범위가 검증된다. | 보완 Q-04, Q-20 | 검증 |

**처리 흐름:** 필드·덱 선택 → 양측 경기 참가 → 기지 배치 → 초기 캐릭터 위치 선택 → 첫 턴. 배치 제한시간, 양측 동시/순차 배치, 상대 배치 공개 시점은 미정이다. 최초 AP는 DEC-007에 따라 VAL-21에서 시작해 첫 턴에 VAL-11을 한 번 지급한다. 초기 장비 제작 재료의 지급 시점은 턴 시작 지급과 중복되지 않도록 정해야 한다.

### 4.2. 필드와 점유

**근거:** 40~49행, [필드](Requirements.md#필드). **연결:** SYS-PRE, SYS-MOVE, SYS-COMBAT, SYS-UI.

| ID | 요구사항 | 확인 기준 | 정의 | 개발 |
|---|---|---|---|---|
| R-MAP-01 | 사각 타일의 자기·중립·상대 필드를 연결해 전장을 구성한다. | 크기와 연결 순서가 VAL-04~06에 맞는다. | 명시 | 완료 |

**확정 규칙 — DEC-008:** 준비 중 예약 가능한 비용 합계는 현재 보유 AP까지다. `예약 AP = 플레이어의 예약 행동 비용 합계`, `사용 가능 AP = 보유 AP - 예약 AP`로 계산한다. 예약을 수정할 때는 기존 예약을 새 예약으로 대체한 합계를 검사하고, 한도를 초과하는 입력은 확정하지 않으며 기존 유효 예약을 유지한다. 예약 취소는 예약 예산을 해제한다. 실제 보유 AP는 예약·수정·취소만으로 변하지 않고 행동 실행 시 소비한다. 아직 획득하지 않은 처치 보상을 기대한 초과 예약은 허용하지 않는다.

**확정 규칙 — DEC-009:** 공격을 정상적으로 실행했다면 적중 대상이 없어도 해당 공격의 AP 비용을 소비한다. 적중 대상이 없다는 이유로 비용을 면제하거나 돌려주지 않으며 한 번의 공격 비용은 한 번만 차감한다. 앞선 단계 사망으로 실행하지 못한 행동의 AP 미소비와 구분한다. 이 결정은 공격 대상 지정 방식·명중 확률이나 그 밖의 실패·대상 소멸·실행 전 취소 비용을 함께 확정하지 않는다.

**예약 AP와 보유 AP는 다른 상태다.** 최초 보유 AP와 첫 턴 지급은 DEC-007, 예약 한도와 준비 중 사용 가능 예산은 DEC-008, 정상 실행한 무적중 공격의 비용은 DEC-009로 보완했다. 그 밖의 실패·대상 소멸·취소 비용과 처치 보상의 지급 시점은 Q-03의 미정 사항이다. 기존 구현의 `확정 시 일괄 차감`을 새 규칙으로 옮겨 적지 않는다.

**현재 코드 확인과 개발 영향:** [BattleResolver.cs](../TurnZero/Assets/ProjectFiles/Prototype/Scripts/Core/BattleResolver.cs)의 `Resolve`는 기본 공격별 피해를 모은 후 HP를 반영한다. 현재 [BattleMatch.cs](../TurnZero/Assets/ProjectFiles/Prototype/Scripts/Core/BattleMatch.cs)의 `ResolveTurn`은 턴 결과를 계산한 뒤 짧은 판정 표시 상태를 거친다. 원문에서 원하는 경로별 이동·투사체·자동 카메라를 재생하는 흐름은 추가 구성이 필요하다. 개발 시에는 기본 공격의 피해 수집 구조를 활용하고, 우선순위별 판정 결과와 그 결과를 보여주는 연출을 분리하는 방향으로 검토한다. 연출 도중 모델이 먼저 사라져 같은 단계의 예약 공격을 보여주지 못하는 문제도 확인한다.

**확정 규칙 — DEC-004:** 양측 기지가 살아 있지만 같은 턴에 양쪽 캐릭터가 모두 전멸하면, 턴 마무리의 남은 기지 HP를 비교한다. HP가 높은 쪽이 승리하고 같으면 무승부로 종료한다. 이 결과를 결정하기 위해 추가 턴이나 부활 유예를 제공하지 않는다.

**확정 규칙 — DEC-006:** 같은 턴에 한쪽 기지만 파괴되고 상대편만 캐릭터가 전멸하면 기지가 파괴된 쪽이 패배한다. 예를 들어 내 캐릭터와 상대 기지가 살아 있는 상태에서 내 기지 파괴와 상대 캐릭터 전멸이 함께 발생하면 나는 패배하고 상대는 승리한다. 이 교차 사례에서는 기지 파괴를 우선한다. 양측 기지 파괴 또는 양측 캐릭터 전멸까지 겹치는 경우의 판정은 별도 결정한다.

**기존 코어 1차 구현 — 2026-10-22:** `BattleResolver.Resolve`에 DEC-004의 상호 전멸 기지 HP 비교와 DEC-006의 교차 패배 판정을 반영했다. DEC-003의 한쪽 전멸 종료와 DEC-005의 양측 기지 파괴 무승부도 코어 테스트로 확인했다.

**현재 로컬 게임 — 2026-10-22:** 새 `BattleSimulation`에서도 확정 승패 규칙을 적용하고, 실제 씬에서 상대 기지를 파괴해 종료·재시작하는 PlayMode 검증을 통과했다. 부활·스킬·장비는 9.3의 로컬 프로필로 연결했다. Q-02의 미정 복합 사례는 기존 무승부를 임시로 유지하며 정식 기획 결정으로 채택하지 않았다.

**현재 문답 진행 — 사용자 요청으로 일시 중지:** DEC-001~009로 동순위 공격·순차 연출·전멸·기지 파괴의 주요 승패 사례·첫 턴 AP·보유 AP 이내의 예약 한도·정상 실행한 무적중 공격의 AP 소비를 결정했다. 사용자는 현재까지 확정된 내용으로 개발을 시작하고 나중에 질문과 결정을 이어가기로 했다. 추가 질문은 사용자가 재개를 요청할 때 이어간다. 재개 지점은 Q-03의 처치 보상 지급 시점이며 그 밖의 실패·대상 소멸·취소 비용과 처치 귀속·중복 보상, Q-01·Q-02 및 다른 미정 항목은 열린 상태로 유지한다. 문답 중지는 규칙 확정이나 구현 완료를 뜻하지 않는다.

**남은 결정 범위 — DEC-009 반영 시점:** 현재 P0는 Q-01~07·Q-17의 **8개 주제**이며 모두 미결정 범위가 남아 있다. 그중 Q-01·Q-02·Q-03은 부분결정이다. 주제는 판정 순서, 사망·승패, AP, 캐릭터 중첩, 이동 경로, 공격 사거리·범위·대상, 쿨다운, 시야·정보 공개다. 한 주제 안에 여러 선택이 있어 8번의 답변으로 끝난다는 뜻은 아니다. 개별 질문 수는 후속 답변에 따라 달라진다. 나머지 P1 14개 주제는 해당 기능 착수 전에, P2 1개 주제는 플레이 검증·출시 범위에 맞춰 보완한다. 편성·필드·준비 완료·온라인 등 다음에 개발할 기능에 필요한 P1 결정은그 기능에 착수하기 전에 확인한다. 전체 23개 주제를 모두 끝낼 때까지 모든 개발을 미루는 조건은 아니다. 현재는 문답을 중지하고 9.1의 착수 방침에 따라 확정 범위부터 진행한다.

**현재 착수 방침 — 2026-10-22 사용자 요청:** 추가 문답을 일시 중지하고 현재 요구사항과 DEC-001~009에서 확정된 범위부터 개발을 시작한다. 아래 착수 조건은 각 묶음의 전체 범위를 구현하기 위한 확인 항목이며 확정된 일부 규칙을 먼저 구현하는 것을 막지 않는다. 미정 규칙은 결정된 것으로 바꾸지 않고 열린 질문으로 남긴다. 미정 사항에 의존하는 세부 기능은 후속 검토 범위로 분리하며 임시 동작을 사용하는 경우에도 확정 규칙과 구분해 기록한다. 이번 문서 갱신 자체는 코드 구현이나 실행 검증 완료의 증거가 아니다.
